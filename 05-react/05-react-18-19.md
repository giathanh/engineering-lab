# React 18/19: concurrent rendering, transitions, Server Components, Actions, `use`

> Mức độ: ⭐⭐⭐ senior | Thời gian đọc: ~10 phút

## 1. Tóm tắt nhanh (TL;DR)

- Concurrent rendering cho phép React prepare, pause/restart và bỏ render work chưa commit để ưu tiên interaction; không đồng nghĩa component chạy trên nhiều JS threads.
- `startTransition`/`useTransition` đánh dấu update không khẩn cấp; input trực tiếp nên vẫn cập nhật tức thời.
- Server Components render phía server, không gửi component implementation/client JS cho phần server-only; chúng khác SSR HTML và có thể phối hợp với Client Components.
- React 19 có Actions, `useActionState`, `useOptimistic`, `useFormStatus` và `use` API; framework quyết định nhiều semantics server-side.
- Suspense/Await integrate với nguồn tương thích; promise cần stable identity/cache, không tạo mới lặp trong client render.

## 2. Khái niệm cốt lõi

React 18 concurrent features cho renderer khả năng interrupt render phase, ưu tiên urgent updates và giữ UI responsive. DOM commit vẫn diễn ra theo phase commit; concurrent không làm side effects trong render an toàn. `startTransition` đánh dấu state update là non-urgent; nếu có urgent update mới, transition work có thể bị restart. Transition không tự debounce network hay giới hạn requests.

SSR tạo HTML trên server để browser hiển thị sớm; hydration gắn event handlers/state ở client. Server Components là component chỉ chạy server trong RSC-enabled framework: có thể truy cập data/server resources, không dùng state/effect/browser APIs, và output được serialize qua RSC payload. Client Components khai báo boundary bằng `'use client'`, có thể dùng hooks/browser APIs và được bundle cho client; module graph phía dưới boundary tăng client bundle.

React 19 Actions tích hợp async form/action state, pending/error/optimistic patterns. `useActionState` quản lý state trả về từ action; `useFormStatus` đọc pending status của form cha; `useOptimistic` hiển thị dự đoán trong lúc action chờ. `use(promise)` đọc Promise và suspend cho đến khi resolve hoặc throw rejection tới Error Boundary; `use(context)` đọc context theo API semantics. Đây không phải thay `useEffect` cho mọi fetch.

## 3. Code ví dụ

Server Action trong React 19 framework hỗ trợ RSC; action chạy server-side và cần validate/authenticate mọi input ở server.

```jsx
'use server';

export async function renameProject(previousState, formData) {
	const name = String(formData.get('name') ?? '').trim();
	if (!name) return { error: 'Name is required' };

	await updateProjectInDatabase(name); // Re-check authorization on the server.
	return { error: null };
}
```

Client form dùng `useActionState(renameProject, initialState)` để lấy state/error/pending; transport/framework integration phải hỗ trợ Server Actions. Không xem action identifier là authorization.

## 4. Trade-off & Best practices

- Dùng transition cho navigation/filtering/render work không cần phản hồi tức thì; giữ controlled input update urgent.
- Tách Server/Client Component theo interactivity và data access; đẩy client boundary xuống thấp để giảm JS bundle.
- Server Components không thay thế authorization/cache policy; server code vẫn cần kiểm tra tenant/user trên từng data access.
- Dùng Actions cho mutation gắn với form/action flow; validate, authorize, handle duplicate submission và invalidation trên server.
- Dùng optimistic UI khi có rollback/error/conflict semantics; giữ server response làm canonical state.
- Bao Suspense/Error Boundaries theo UX/loading/error ownership; promises cần được tạo/cached theo framework guidance.
- Kiểm tra hydration mismatch: server/client output phải tương thích với locale/time/random/browser-only data.

## 5. Lỗi thường gặp / Pitfalls

- Nghĩ concurrent rendering là multithreaded JavaScript hoặc mọi update tự interruptible.
- Đặt `'use client'` ở root rộng, vô tình kéo cả dependency graph vào bundle.
- Đưa secret/server-only code qua Client Component props hoặc import boundary.
- Tạo `Promise` mới trong Client Component mỗi render rồi truyền vào `use`, gây suspend liên tục.
- Tin Server Action tự xử lý authorization/CSRF/business invariants.
- Dùng transition cho input value cần synchronous feedback.
- Optimistic update không rollback khi action reject.

## 6. Câu hỏi phỏng vấn

<details>
<summary><b>Q1. Concurrent rendering có nghĩa gì?</b></summary>

React có thể schedule, yield, restart hoặc abandon render work chưa commit để ưu tiên update. Component vẫn chạy trên JavaScript runtime thread; render cần pure.

</details>

<details>
<summary><b>Q2. Transition khác debounce?</b></summary>

Transition đánh dấu render update có priority thấp hơn; debounce trì hoãn/giảm số lần gọi một operation theo thời gian. Chúng giải quyết vấn đề khác nhau.

</details>

<details>
<summary><b>Q3. Server Components khác SSR thế nào?</b></summary>

SSR tạo HTML; Server Components là component execution/data model trong RSC framework, có thể stream payload và tách client code. Chúng có thể phối hợp nhưng không đồng nghĩa.

</details>

<details>
<summary><b>Q4. `'use client'` tạo boundary gì?</b></summary>

Đánh dấu module là Client Component entry; imports phía dưới trở thành client dependency graph. Boundary quyết định hooks/browser APIs và bundle ownership.

</details>

<details>
<summary><b>Q5. `use` API xử lý Promise rejection ra sao?</b></summary>

Pending promise suspend; fulfilled trả value; rejection được ném để Error Boundary/framework xử lý. Nguồn Promise/cache stability quan trọng.

</details>

<details>
<summary><b>Q6. Server Action có tự an toàn không?</b></summary>

Không. Mọi input từ client không tin cậy; action cần authentication, authorization, validation, rate/abuse controls và idempotency phù hợp.

</details>
